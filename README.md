## 🔧 给发行仓库维护者

以下是发布与维护流程摘要，普通用户无需执行。

### 问题包目录结构

由工作室执行“导出发布包”后，将完整的新问题包目录加入本仓库根目录，而非把草稿或旧问题重新打包：

```text
questions-<timestamp>-<id>/
├── bundle.json
├── review.json
└── audio/
    └── \\\*.wav
```

* `review.json` 必须对应实际完成人物表达、剧情事实、日语翻译、称谓、发音和情绪审阅后的内容。审核记录绑定正文及音频文件路径、大小与 SHA-256；修改后需要重新审核导出。机器检查不能代替人工审听。
* 发布检查包含题目／分段 ID 唯一性、段序、人物姿势 ID、非空日语、WAV 结构、路径和哈希。已发布问题 ID 不得以新目录重复发布。
* 单个 `bundle.json` 上限 **10 MiB**，单 WAV 上限 **20,000,000 字节**，单包正文与音频总上限 **500,000,000 字节**；单包最多 **1,000 题**、单题最多 **100 段**。全库最多 **20,000 题／1,000 包／2,000,000,000 字节**，清单最多 **5,000,000 字节**。
* 每次发布都需要保留原来已发布的问题包及仍被引用的资源。发布前可以运行 `node scripts/publish-catalog.cjs --check` 做预检查（需按脚本要求配置 `GITHUB\\\_REPOSITORY`、`GITHUB\\\_SHA`、新的 `CATALOG\\\_OUTPUT` 路径）。

### 签名及更新通道

本仓库的 GitHub Actions 在问题包和脚本相关路径发生变更时执行检查；工作流位于 `.github/workflows/publish.yml`。问题目录的发布使用 Actions Secret `QUESTION\\\_SIGNING\\\_PRIVATE\\\_KEY` 中的 **Ed25519 私钥**签名。客户端使用内置可信公钥验证清单和资源，不能从未签名的远端内容学习公钥。

检查通过后，工作流创建新的 `catalog-\\\*` Release，包含 `release-manifest.json` 和 `release-manifest.sig`，并把对应的已核验 Git commit 写入签名清单。**只有问题目录 Catalog 使用 latest；客户端和语音环境的发行不要抢占这一位置。**

冲突和失败由 Actions 日志及 `question-catalog-conflicts` 附件记录；任何失败不得当作空目录、跳过签名检查或自动删除旧发布资产。旧客户端的问题包大小与同 ID 音频替换支持可能不同，应按客户端版本限制处理。

### 已发布语音的替换

确实需要替换旧问题的配音而保持正文时，使用仓库根目录 `audio-replacements.json` 的明确声明流程：绑定当前签名目录、原目录和 `content\\\_hash`，新包保留原问题 ID、顺序、正文、译文、假名稿、分段、立绘和来源记录，仅按协议替换音频引用，并重新人工试听、生成 `review.json`。未经声明的删除、重复 ID 或正文变动应继续拒绝；历史 Release 与 Git 提交保留供追踪恢复。
